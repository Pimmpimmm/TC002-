# TC002 boundary evidence — 2026-09-02

## What the official material proves

- TC002 is 52×16 and stock software has a native BUSY Clock. The task and the user's 2026-09-01 confirmation establish middle-button entry/exit behavior; the public page confirms BUSY as a continuously red native tool but does not document its outbound event.
- Studio V3.1.0+ can configure TC002 MQTT. The official tutorial says a subscription topic may monitor reports, but supplies no standard prefix/topic/schema. Its publish example draws “Hello World” on the DIY page; it is not a transient notification and is not evidence of automatic return.
- The device source repository is explicitly about compiling/flashing replacement apps. That route violates this task.
- The Studio plugin SDK is not a bridge to stock TC002 BUSY: its published supported-device list omits TC002, and its input events belong to configured plugin actions. No source says stock BUSY starts a plugin or forwards its entry/exit.

## Repository-level audit (2026-09-01)

- The official GitHub organization exposes the TC002 device-development repository plus the Deck plugin SDK/common libraries. At audited commits `d84f52a1...` (TC002) and `550ab80c...` / `9e478b25...` / `0aeb6a26...` (plugin SDK/common libraries), a full-tree search found no stock `BUSY`/Pomodoro implementation or public stock-page lifecycle event.
- `Z21_TC002_Demo/src/managers/KeyManager.h` defines `E_KEYCODE_MIDDLE_BUTTON = 0x69`, and the demo can register a local `KeyManager` callback. This proves hardware input is accessible **inside a compiled FlyThings device application**. The repository README explicitly scopes that code to writing, compiling and flashing/downloading an application; it does not prove that the installed official clock publishes the key or BUSY state externally.
- `apps/mqtt/README.md` explicitly marks the standard broker/topic/payload/authentication contract as “待官方补充”. Its current examples are inbound `mqtt.publish` payloads for Custom App display. None defines a BUSY-enter, BUSY-exit, current-page or retained-state report.
- The public Studio manifest contract says an Action is assigned to a device key and lists `D200`, `D200H`, `Dial`, `D200X`; it does not list TC002. Therefore `keydown`/`keyup` in the public plugin SDK are not evidence for the TC002 middle key.
- Read-only inspection of the installed Studio bundle found an official `PrivateAPI: true` TC002 plugin whose description and actions are D200-family → TC002 LAN remote control, including a “Busy Mode Toggle”. That proves an internal **command** path exists, not a TC002 physical-key → Mac **observation** path. Its private protocol is not a reliable public architecture contract.
- A second read-only scan of the installed executable found `Tc002Client::sendAction`, action values constrained to `0–4`, and the command strings `ccw`, `knob`, `shortPress`, `middle`, plus the Busy icon. The readable TC002 HTTP paths are configuration/data routes such as `/getBase`, `/getMqttConfig`, `/getToolsConfig` and corresponding setters; no readable current-page/current-BUSY query or reverse key callback was found. `/getToolsConfig` sits beside `focusTime`, `relaxTime`, `busy`, `tomato`, `toolsInfos` and `toolsOrder`, so it remains only a read-only **configuration comparison candidate**, not proof of live state.

The public-source verdict is therefore precise: native BUSY exists and the hardware key is programmable in replacement apps, but stock-firmware BUSY entry/exit observability is undocumented. The real-device capture below now also rules out BUSY reports on the public/proven stock MQTT and read-only HTTP surfaces of firmware `1.1.1`. Only a firmware-specific official topic/endpoint answer or changed stock-firmware behavior can reopen that verdict.

## Official MQTT tutorial re-check (2026-09-02)

The official forum tutorial is useful for the transport setup, but it does not close the native-BUSY evidence gap:

- It confirms Studio V3.1.0+ can save a local broker address/port for stock TC002 and that the broker can observe TC002 as a connected MQTT client. This validates the planned private-broker capture setup.
- The MQTTX screenshots use `[device-prefix]/custom/display`, QoS 0, and a non-retained publish. The JSON contains display primitives and the result appears only after switching TC002 to its DIY module. This proves the inbound route `Mac/broker -> TC002 DIY display`.
- Although the prose calls subscription a way to monitor TC002 reports, the screenshot subscribes to the same `/custom/display` command topic. A broker echo of another client's publish is not proof that TC002 originated a report.
- The tutorial contains no BUSY/middle-key/current-page topic, no outbound payload schema, no retained current state, and no reconnect recovery contract. Therefore it cannot yet drive Lark calendar creation from the native button.

Practical decision: reuse the tutorial's broker configuration procedure for the 90-second wildcard capture, but do not publish its “Hello World” payload during that test and do not treat `/custom/display` as the BUSY event topic.

## Real-device MQTT/HTTP result (2026-09-02)

- The user explicitly authorized a temporary MQTT target change. Studio showed the TC002 connected; device firmware remained `1.1.1`, MCU `V1.0.17`, Studio `3.2.11`, native BUSY `45+5`, and the saved base prefix `ulanzi`.
- Aedes `1.1.2` listened only on the Mac's trusted-LAN IPv4:1883. Initial red tests correctly exposed two TC002 compatibility details: the configured base prefix becomes `[prefix]_[device]/...`, and the CONNECT packet carries zero-length username/password fields. The broker was narrowed to accept only that derived topic shape and empty credentials; non-empty credentials and unrelated topics remain rejected.
- Green connection evidence: TC002 authenticated and published retained `[PREFIX]_[DEVICE]/status` with the content-free value `online`, published a non-retained `getBase` packet once, and subscribed to `[PREFIX]_[DEVICE]/custom/+` and `switchDiyApp`. This confirms the official tutorial's stock MQTT transport and DIY command direction.
- First 90-second capture was invalid after T+45 because the probe advertised a 30-second keepalive without sending PING. The client now advertises 120 seconds. The second run stayed connected for the full 90 seconds and captured only the retained `status=online` replay at T+0; the broker recorded no additional TC002 publish in the four requested action windows.
- On 2026-09-02 the user confirmed that the physical T+10/T+25/T+40/T+55 operations and multiple extra native BUSY switches were performed during the valid second capture. The zero-event result is therefore promoted to a **verified physical negative** for firmware `1.1.1`'s proven stock MQTT surface. This does not claim that no unpublished or future official interface can exist.
- Read-only live HTTP returned `200` for both candidates. `/getBase` contains only identity/network/version fields. `/getToolsConfig` contains static tool configuration (`busy.focusTime/relaxTime/enable`, Tomato, weather, order, etc.) but no current page, live BUSY phase, start time or deadline. It is not a BUSY observation source. Re-run without exposing raw values: `TC002_FROM_STUDIO=YES npm run probe:tc002:http`.
- Restoration was verified from the device itself: `isMqtt=false`, address empty, port `1883`, prefix still present, username/password empty and HA discovery off. TCP 1883 had no listener after shutdown. BUSY/tool settings were unchanged and no display payload was sent.

## Transient notify gate

No official topic/HTTP route or payload for a stock-firmware temporary overlay was found. `probes/tc002-notify.mjs` therefore refuses to invent one: a candidate must be supplied from an official TC002 source or captured Studio request. Execute only while filming and only with `TC002_ACK_DEVICE_TEST=YES`. Pass requires immediate overlay, visible ≤5 seconds, automatic return to the exact prior native screen, and unchanged settings. `setConfig/carouselSpeed`, custom/FlyThings apps, TC001 and AWTRIX are excluded.
